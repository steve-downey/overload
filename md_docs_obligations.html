The plan's table holds the predictions. This one says what the model found, and where the prediction failed. The classes are the plan's: by construction, compiler-checked, library-checkable, undiagnosable.

Every row of the plan's table has its theorem or its counterexample.

Two layers, three overload sets

A typeclass in beman.transpose has two layers, and the rows below say which one they are about.

  • The instance is the bundle of operations, and it is the primary interface: an object such as OptionalFunctorMap<V> or optional_applicative_map<V>, whose members are the typeclass's operations. The lookup variable functor<T> or applicative<T> names it, and a user calls its members directly: const auto &app = applicative<std::optional<int>>; app.invoke(f, x, y).
  • Each named operation is also an operation object of its own, a secondary interface over the first: struct fmap_fn with exactly one operator() template, and inline constexpr fmap_fn fmap{}. Its operator() finds the instance through a trailing const auto &TC = functor<std::remove_cvref_t<T>> and is constrained on TC.fmap(...). It is shaped like a customization point object, but it dispatches through the lookup variable, not through argument-dependent lookup or tag_invoke.

A call meets three overload sets, and they have different owners.

  • The member call app.invoke(...) or TC.fmap(...), on the instance's members, such as derive_functor's constrained fmap and replace. It is the primary interface, and the operation object's constraint and body are this call. Member lookup finds the members of one class, and argument-dependent lookup does not run for a member call. That overload set belongs to the derivation base and the instance author. The model does not resolve it: it is an atomic constraint, true when the lookup selects an instance. The row for accurate member constraints is what makes that atomic honest (findings).
  • The call fmap(f, x). Name lookup finds the variable fmap, so the candidates are that object's one operator(), and nothing else: a variable cannot be overloaded, and argument-dependent lookup adds no candidates when ordinary lookup finds an object. The model resolves this call, with the operation object as its only function template (fmapObject). If a typeclass author made fmap a function template or an overload set instead, users and argument-dependent lookup could add overloads, and the rows marked for a design with overloads apply.
  • A pinned call, tc.fmap(f, v), on an instance object the caller names in place of the lookup. It is a member call too, and never goes through an operation object.

Shapeless default: std::false_type has no instance's shape. Typeclass author byValue_omitted_outcome Library-checkable: one static_assert per typeclass. Held.
Normalized lookup key: cv and reference qualifiers are removed before lookup. Typeclass author fmapObject_outcome, unpinned_deduce By construction: the operation object looks up at std::remove_cvref_t<T>, and a const C & parameter deduces C without them (op_object_normalized_key). Held.
No other lookup on the name: the other candidates of a call such as fmap(f, x) do not reach the lookup. Typeclass author call_stability By theorem for an operation object with one operator(): lookup of fmap finds the object, which suppresses argument-dependent lookup ([basic.lookup.argdep]/1) and makes the class's call operators the whole candidate set ([over.call.object]/1), so no other candidate exists (object_design_candidates, call_stability_object); a function of the name in the object's scope would conflict with it ([basic.scope.scope]/6). Also held for fold_map and combine_all, whose objects each have two operator()s of different arity: the shorter call cannot deduce the parameter that precedes the lookup default in the longer one, so that candidate fails before it reaches the lookup (arity_disjoint_soft, call_stability_arity). With the default placed first, a longer operator() reaches the lookup in a shorter call, and an ambiguous lookup makes a call meant for another operator() ill-formed (arity_order_matters). Live where a named operation is a function template or an overload set, since anyone can add an overload of that name: each added overload must not consult the lookup. A design with route overloads must meet it per overload. Not predicted. Refined: an operation object may have several operator()s if no other one reaches the lookup.
Placement: in an overload set of routes, a call meant for an explicit route never substitutes the canonical overload's default. Typeclass author, for a design with route overloads the routes as alternatives By construction for the value and argument routes, which fail the canonical overload on kind or arity first. Not met by the type route (routes_type_ambiguous_hard). The library has no route overloads, so it owes nothing. Not predicted.
Instance identity: two uses with different instances are different specializations. Typeclass author instance in the type By theorem for pinning: a reference argument is the object it designates, and two objects are two specializations (reference_keeps_identity, pin_keeps_identity, [temp.type]/2). By construction for the type route. For the value route up to value equivalence, which for empty instances is the type; and a value parameter typed at a base slices a derived instance to it (slicing_identifies, value_route_slices), while the library's instance types are not structural and cannot take the value route at all (value_route_needs_structural). The plan's structural-identity row assumed value parameters; the library uses references, and phase 10 shows a value parameter would slice.

Visible overloads, for a free-function design: every overload of an operation that argument-dependent lookup could find is declared where every dependent call's definition or instantiation context sees it. Not predicted. Vacuous for the library, by its design.
Visibility and stable satisfaction: every instance is declared before any use, the same in every translation unit. Instance author, everyone call_stability_unit, verdicts_single Undiagnosable, by two rules. An instance declared after a use in the same unit gives the lookup a second point of instantiation with a different meaning ([temp.point]/7). An instance of another unit that a use would select is not reachable from it ([temp.spec.partial.general]/1). The model reports either as a verdict on the program and says nothing more (IllFormedNdr, missing_instance_verdict, late_instance_verdict). For one unit, no verdict is exactly the standing assumption (verdicts_single). Per unit, a call sees what precedes it, and an instance after it is either inert or a verdict (call_stability_unit, late_insertion_verdict). Held: undiagnosable, now tied to rules.
Instance placement: an instance for a type is declared in a header that every use of its lookup on that type must include, which for a std type is the typeclass's header. Typeclass author, for instances of std types; instance author otherwise call_stability_unit, verdicts_single Not met by beman.transpose for std::array, std::expected, std::simd::basic_vec (Applicative, and Monad for std::expected) or for std::vector (Foldable, Traversable): each is declared in a header of its own. Met for library types, whose instances sit in the type's header. A late include is ill-formed with no diagnostic required: GCC 16 diagnoses it and Clang 23 keeps the stale answer (probes). Met by a user who includes the umbrella header everywhere (convention). Not predicted. Failed for the std instances outside their typeclass's header.
Instance in the signature: a function whose behaviour depends on an instance names the instance itself among its template arguments. Typeclass author and user divergence-separation Not met by the library's operation object, which names the lookup variable, one entity in every unit (sameEntity, [basic.link]/8). Two units whose lookups differ give one specialization two meanings, ill-formed with no diagnostic required by [basic.def.odr]/16 (operation_object_not_separated; the verdict is odrMismatch at the lookup, Units.odrVerdicts, and a verdict of phase 8 is already there, odr_verdict_implies_verdict). Met by pinning, which names the object (superclass_identity), and by the by-value policy as far as instance types are distinct (byValue_separated). Failed for the canonical route: a template argument is not enough when it is a reference to the lookup.
Distinct instance types: two instances of one typeclass are objects of different types. Instance author byValue_separated Convention. The by-value route identifies an instance by its type alone, so two instances of one type are one specialization. Not predicted.
Exact-type use: every conversion a call forms meets a class whose derivation would be erased at that class's exact type, and no such class is deduced from as a derived class. Naming no instance type in a signature, not even as derive_functor<I>, nor the implementation an instance inherits protected, is the practical rule. Author of an overload on instances, user of the library inheritance_erasure; rank_beats_refinement, derived_class_deduction and erasure_needs_exact_type show the failure Undiagnosable as a rule. Each overload is well-formed, and the call moves to the less refined overload without a diagnostic once one instance type derives from another (leak_rank_derived). No rule makes such a program ill-formed: it is well-formed and calls what the author did not mean. A protected base is no shelter: a signature naming the implementation is selected and the call is ill-formed at the inaccessible conversion (protected_base_selected_ill_formed). Held: leak 1 is live, as predicted. The hypothesis is about conversions, not signatures, because a parameter deduced from one argument can meet a derived class in another.
Superclass coherence: a superclass instance retrieved from a stronger one behaves as the canonical instance where one exists. Instance author superclass coherence Undiagnosable. The two are different template arguments (superclass_identity), so they can agree only in behaviour, which the model does not have. The library's as_functor deliberately does not consult the canonical lookup. No rule makes disagreement ill-formed: the program is well-formed with two Functors. Held: a law, as predicted.
Visible refinement: a refinement between conditions is written as constraints, so subsumption can see it. Typeclass author sfinae_requires_resolve; sfinae_loses_subsumption shows the failure Convention. An enable_if encoding of the same condition is accepted, has the same viable set, and loses every ordering a requires-clause would win, without a diagnostic. It also gives up the shielding of the function type (sfinae_unshielded). In beman.transpose, monad_object is not written over applicative_object, and no registered object satisfies both (probes), so nothing depends on the refinement today. A user object that satisfies both makes overloads on the two concepts ambiguous. Held, with step order added.
Decreasing requirements. Instance author termination Vacuous for the library: no instance requires another. Not needed today.
Accurate algorithm constraints: an algorithm offered for others to constrain on states as its constraint the member calls its body makes, with each guard before the call it protects. Algorithm author soft failure through the algorithm: with that constraint it answers as its members do, call by call in the order written (algorithm_transfer), and it is accurate when they are (algorithm_accurate); a guard written after the call it protects protects nothing (call_order_matters) Convention. Met by the library's traverse and transpose objects on every probe, and by the folds, whose test for a registered Monoid is written before the call that names one. An algorithm that nobody checks owes nothing: a weaker constraint is a hard error at its call, never a program that compiles and should not. Not predicted. Beyond the model

The algorithm probes (probes) found three more obligations on an algorithm handed an instance. No theorem needs them, because the model has one instance per key and no copies or state. They are weighed in the plan.

Obligation Owed by Discharge found
The instance given is the instance used: an algorithm takes every operation on a context from the object it was handed, never from the lookup or a stronger typeclass's lookup. An alternative instance that changes values has its own carrier; one that changes only evidence may share the carrier as an explicit object. Algorithm author; typeclass author, for carriers Convention. One slip to bt::invoke or bt::bind under the accumulating applicative keeps the first error and drops the rest, and compiles. The library's derived members and traverse use the object given. The library meets the carrier rule: the zip applicative is zip_list's, and the accumulating applicative is reached only by name.
Instance state: an algorithm uses the object it was passed, or requires std::is_empty_v of a type it constructs. Algorithm author Not met by lifted_monoid and kleisli_monoid, which construct their object from its type, so a stateful one is never consulted. Every registered typeclass object is empty, so no library result is affected. traverse takes the object. Monoid objects may carry state, and lifted_monoid does.
Callable identity: an algorithm that needs the caller's callable, not a copy, passes std::ref. Algorithm author, user Convention, as for the Standard's algorithms ([algorithms.requirements]/9). zip_list's invoke runs a copy of an lvalue callable. std::ref keeps identity through every instance probed.
