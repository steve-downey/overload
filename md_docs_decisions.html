instance-inheritance

Question: May instance types for related typeclasses be related by inheritance? Status: DECIDED 17 October 2026. Decision: Allowed. Inheritance between instance types is a choice an implementer can make, and the model treats it as one. The work is to find the problems it causes and say, for each, whether it is a matter of education, an obligation on someone, or a bug to fix. Why: The point of the work is to state what a typeclass implementer owes. Forbidding inheritance would only be worth it if it were harmful, and it would then need a technical means of enforcement, which is unlikely to exist. So it is allowed, and its consequences are harvested as obligations (obligations.md): exact-type use, and superclass coherence. Decided by: the author. Facts recorded 13 October 2026: The relation varies by kind and may vary within a kind, since not every Functor is an Applicative and a type may admit more than one instance. Where a relation exists it runs from the stronger class to the weaker. A Monad instance offers as_functor, which returns derive_functor<M>, a fresh type that supplies the Functor operations from the Monad ones. Log:

  • 2026-10-13 — Opened.
  • 2026-10-15 — Leak 4 (constant-parameter conversion) is live under C++26 per the probe verdicts: a derived instance supplied as a literal template argument for a base-typed constant parameter is sliced and identified with the base value. The exact-type obligation now covers constant parameters as well as function parameters.
  • 2026-10-17 — Evidence for an answer, not a ruling. Inheritance erasure is proved for the model's fragment (inheritance_erasure). Erasing the base classes of a set of instance types changes no call that uses every class erasure touches at its exact type. Outside that fragment erasure changes outcomes (erasure_needs_exact_type, rank_beats_refinement). Superclass coherence is a law, since a retrieved Functor and the canonical one are different template arguments (superclass_identity). The proposed answer is the plan's guidance: inherit if you like, but never name an instance type in a signature, and keep a retrieved superclass instance law-compatible with the canonical one. Two gaps remain before it can be settled. Deduction from a derived class (leak 2) is not modelled, and neither is access to the protected base that derive_functor uses. Update the same day: leak 2 is now modelled and is a theorem (derived_class_deduction), and erasure asks that no argument of a touched class be deduced from as a derived class. Access to a protected base is the gap that remains. beman.transpose relates no two instance types by public inheritance: derive_monad grows only the Functor basis, and as_functor returns derive_functor<M>, which has M as a protected base.
  • 2026-10-17 — Decided by the author: allowed. The known problems are leak 1 (rank beats refinement), leak 2 (deduction from a derived class), leak 3 (two paths to the superclass) and leak 4 (constant-parameter slicing), all recorded as obligations. Access to a protected base is still unmodelled, and is the next place to look for a problem.
  • 2026-10-17 — Access is modelled (Overload/Access.lean). A protected base, as derive_functor has, does not hide the implementation from overload resolution: ranking ignores access, deduction from a derived class goes through the base, and a selected conversion to it makes the call ill-formed (protected_base_selected_ill_formed, protected_base_deduced_ill_formed). It is the exact-type obligation again, with the implementation's types among those a signature must not name.
  • 2026-10-21 — Phase 10 makes leak 4 a theorem: a derived value supplied for a base-typed value parameter is sliced to the base subobject, and the two name one specialization (slicing_identifies). A reference parameter denotes the object, so the library's const auto& parameters are what closes the leak (reference_keeps_identity).

explicit-instance-routes

Question: Which ways of supplying an instance other than canonical lookup does the model cover? Status: DECIDED 16 October 2026. Decided by: the author. Decision: Both. First the library as written: the operation object with its const auto & instance parameter, the user-side pinning pattern, and the by-value trailing argument. Then the plan's three routes, as alternative designs, so the guidance can compare them. Why: The library is what the theorems have to be about. The plan's routes are designs someone might adopt, and the inheritance guidance is stronger when it can say which of them a leak depends on. Facts recorded 16 October 2026, from beman.transpose (the typeclass repository's include/beman/transpose/):

  • Each named operation is its own operation object (fmap, replace, bind, join, and the applicative and fold objects), and each object has one operator(). It looks the instance up through a trailing const auto &TC constant template parameter defaulted to the lookup, constrained on the call through TC. There are no overloads between routes, no priority tags and no rank types. The library's own comment calls naming TC explicitly "a curiosity, not an API".
  • What the plan called the three routes appear as patterns, not as overloads. An instance can be called directly (tc.fmap(f, v)). User code can pin one through its own const auto & constant template parameter defaulted to the lookup. A few objects take one by value as a trailing function argument: traverse takes a POLICY that defaults to the applicative lookup and is constrained by applicative_object_for, and fold_map and combine_all have an extra-arity overload taking a monoid. Library-provided instances take others as type template parameters and default-construct them (lifted_monoid, the Kleisli monoid).
  • Constant template parameters for instances are references bound to the inline constexpr lookup variables, never structural values. Instance types are empty. Monoids may carry state, and are passed by value only.
  • No instance is conditioned on another instance at a subterm, so lookup never recurses.

Log:

The model's Val covers values only.

scope-syntax

Question: How do scopes enter the program syntax? Status: DECIDED 20 October 2026. Decision: A scope is a field. Each namespace-scope declaration (Decl.function, Decl.functionTemplate through FunctionTemplate, Decl.class, Decl.classTemplate, Decl.object) carries scope : Scope := [], a path of namespace and class steps from the global scope outward in. A member function is a function whose scope ends in its class; Decl.class gains no member list. An object carries the name of its class, so a call on it has a scope to search for operator(). The program stays a flat list, lookup is a layer in front of resolve, and the found declarations are handed to the existing resolution with Candidate.index their position in the found list, as generate numbers candidates today. Why: Counted against the sources on 20 October 2026: eleven pattern sites on Decl.function, fifteen on Decl.functionTemplate, five on Decl.class, two on Decl.object, two exhaustive matches, eight inductions on the candidate list and none on the program, and about fifteen theorems that reason positionally on the flat list (declaredBeforeUse, stability, the verdicts of Units, call_stability_unit). A field with a default leaves every program literal, every induction and every positional theorem as it is. A nesting constructor Decl.namespace (decls : Program) breaks the positional theorems and makes every new structural proof a nested recursion. A side table or enter-and-leave markers make a declaration's scope a function of its prefix, so every insertion lemma would need a balanced-markers hypothesis. A member list on Decl.class is a nested inductive again and breaks eraseBases, directBases and allBases. Decided by: the author, on the design review of 20 October 2026. Facts recorded 20 October 2026: an omitted trailing default field in a Lean pattern elaborates to the default value, not a wildcard, so | .function _ _ => true is false on a namespaced function. Every existing match on a declaration therefore gets an explicit placeholder, and a guard checks that a namespaced function is seen, because the compiler will not say. Log:

  • 2026-10-20 — Decided.
  • 2026-10-20 — Landed. ScopeStep, Scope and the fields are in Overload/Program.lean; every existing program literal, proof and emitted case is unchanged, as the counts predicted. One correction on the way: two declarations are one entity only when they also declare the same kind (sameEntity), or an object and a function of one name would merge instead of conflicting.

value-typing

Question: Does a constant template argument value carry its type? Status: DECIDED 21 October 2026. Decision: No. Val stays an untyped tree. The source type of an explicit value is the literal's by [lex.icon]/3 for an integer, bool for a bool, and the class for a class value (Val.sourceType). Deduced values are not converted and not typed: [temp.deduct.type]/20, which requires the type of a deduced i to equal the parameter's type in the specialization it was deduced from, stays uncovered. Why: Typing Val would reach into every deduction proof for a rule the typeclass encoding never exercises: its constant parameters are references to the lookup variables and auto, and the explicit-instance routes pass class values. Out of the fragment for the same reason: floating-point values, pointers and pointers to members, arrays, enumerations, unions, closure types, user-defined conversions and converting constructors, braced-init-lists, decltype(auto) parameters. Decided by: the author, on the plan of 21 October 2026. Log:

  • 2026-10-21 — Decided.
  • 2026-10-21 — Landed: Val.sourceType and literalType in Overload/Arguments.lean. narrowing_constant is the reason the typing is not missed: for a constant, the source type decides nothing the value does not (findings.md).
