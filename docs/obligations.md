# Obligations

This is the obligations table that [the plan](plan.md#proof-obligations) calls for,
as harvested so far. Each row is a hypothesis that a proved theorem needs
and the language does not guarantee. The plan's table holds the
predictions. This one says what the model found, and where the
prediction failed. The classes are the plan's: by construction,
compiler-checked, library-checkable, undiagnosable.

Every row of the plan's table has its theorem or its counterexample.

## Two layers, three overload sets

A typeclass in beman.transpose has two layers, and the rows below say
which one they are about.

- The instance is the bundle of operations, and it is the primary
  interface: an object such as `OptionalFunctorMap<V>` or
  `optional_applicative_map<V>`, whose members are the typeclass's
  operations. The lookup variable `functor<T>` or `applicative<T>` names
  it, and a user calls its members directly: `const auto &app =
  applicative<std::optional<int>>; app.invoke(f, x, y)`.
- Each named operation is also an operation object of its own, a
  secondary interface over the first: `struct fmap_fn` with exactly one
  `operator()` template, and `inline constexpr fmap_fn fmap{}`. Its
  `operator()` finds the instance through a trailing `const auto &TC =
  functor<std::remove_cvref_t<T>>` and is constrained on `TC.fmap(...)`.
  It is shaped like a customization point object, but it dispatches
  through the lookup variable, not through argument-dependent lookup or
  `tag_invoke`.

A call meets three overload sets, and they have different owners.

- The member call `app.invoke(...)` or `TC.fmap(...)`, on the instance's
  members, such as `derive_functor`'s constrained `fmap` and `replace`.
  It is the primary interface, and the operation object's constraint and
  body are this call. Member lookup finds the members of one class, and
  argument-dependent lookup does not run for a member call. That overload
  set belongs to the derivation base and the instance author. The model
  does not resolve it: it is an atomic constraint, true when the lookup
  selects an instance. The row for accurate member constraints is what
  makes that atomic honest
  ([findings](findings.md#about-the-library)).
- The call `fmap(f, x)`. Name lookup finds the variable `fmap`, so the
  candidates are that object's one `operator()`, and nothing else: a
  variable cannot be overloaded, and argument-dependent lookup adds no
  candidates when ordinary lookup finds an object. The model resolves this
  call, with the operation object as its only function template
  (`fmapObject`). If a typeclass author made `fmap` a function template or
  an overload set instead, users and argument-dependent lookup could add
  overloads, and the rows marked for a design with overloads apply.
- A pinned call, `tc.fmap(f, v)`, on an instance object the caller names
  in place of the lookup. It is a member call too, and never goes through
  an operation object.

## Beyond the model

The algorithm probes ([probes](probes.md#algorithm-probes)) found three more
obligations on an algorithm handed an instance. No theorem needs them,
because the model has one instance per key and no copies or state. They
are weighed in [the plan](plan.md#algorithm-author-obligations).

| Obligation | Owed by | Discharge found |
|---|---|---|
| The instance given is the instance used: an algorithm takes every operation on a context from the object it was handed, never from the lookup or a stronger typeclass's lookup. An alternative instance that changes values has its own carrier; one that changes only evidence may share the carrier as an explicit object. | Algorithm author; typeclass author, for carriers | Convention. One slip to `bt::invoke` or `bt::bind` under the accumulating applicative keeps the first error and drops the rest, and compiles. The library's derived members and `traverse` use the object given. The library meets the carrier rule: the zip applicative is `zip_list`'s, and the accumulating applicative is reached only by name. |
| Instance state: an algorithm uses the object it was passed, or requires `std::is_empty_v` of a type it constructs. | Algorithm author | Not met at `30a707d` by `lifted_monoid` and `kleisli_monoid`, which constructed their object from its type, so a stateful one was never consulted; met at `5d248b9`, where both hold the object and a stateful one passed in is consulted ([probes](probes.md#algorithm-probes)). Every registered typeclass object is empty, so no library result was affected. `traverse` takes the object. Monoid objects may carry state, and `lifted_monoid` does. |
| Callable identity: an algorithm that needs the caller's callable, not a copy, passes `std::ref`. | Algorithm author, user | Convention, as for the Standard's algorithms ([algorithms.requirements]/9). `zip_list`'s `invoke` runs a copy of an lvalue callable, and since `5d248b9` its constraint says so. `std::ref` keeps identity through every instance probed. `copy_constraint_shields` (phase 12) is the rule as a theorem: `is_copy_constructible` as a constraint makes the call not viable at a callable whose copy constructor is deleted, where the same trait as a Mandate makes it ill-formed. |
