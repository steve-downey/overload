Modelling C++ overload resolution in Lean: plan

Steve Downey, 13 October 2026. Transcribed into the repository on 15 October 2026; the decision log has moved to decisions.md, the probe results to probes.md, and the standing findings to findings.md. Items settled since are marked.

Purpose

Build a Lean 4 model of the C++ selection mechanisms that the pure-library typeclass technique depends on, and use it to show that the open polymorphism it provides is sound and unsurprising.

The model covers template argument deduction, substitution failure (SFINAE), Concepts constraints, Mandates, partial ordering, partial specialization matching, and overload resolution. The typeclass encoding is then defined on top of the model, and its properties are proved about that definition.

Three deliverables:

  1. Stability theorems. Instance lookup is coherent, and adding an instance cannot silently change the meaning of code that already resolved.
  2. Inheritance guidance. A proved answer to whether instance types for related typeclasses (Functor and Applicative) may, should, or must not be related by inheritance.
  3. An obligations table. The proof obligations a typeclass places on its authors and users beyond the algebraic laws, each classified by how it is discharged.

A fourth outcome is possible and would matter beyond this work: a place where a supposedly well-understood part of the language behaves differently once constant template parameters carry instances. The plan is arranged so that such a result shows up as a specific failed proof.

Two further results are about the Standard itself. Some statements it spells out will turn out to be theorems of its other rules, and identifying them is useful. A statement that is inconsistent with the rest, or false, would be a defect. That is not expected, but the model is built so it could not pass unnoticed.

Scope

The core is smaller than full overload resolution. Instance lookup runs through variable-template partial specialization, which the standard defines by rewriting to function-template partial ordering plus constraint subsumption. Call-site overload resolution is a layer above that core.

In scope:

  • Template argument deduction for type and constant template parameters, including default template arguments and non-deduced contexts.
  • Substitution with three outcomes: success, deduction failure, and hard error.
  • Constraints: normalization, atomic constraint identity, satisfaction, subsumption.
  • Mandates, modelled as a check that runs only after selection.
  • Partial ordering of function templates, and matching and ordering of partial specializations.
  • Best viable function selection, with implicit conversion ranking supplied as a parameter.
  • The typeclass encoding: canonical lookup, the three explicit-instance routes, and customization point objects that dispatch to an instance.
  • Since phase 12: the type categories of [basic.types], data members and function types; the special member functions, implicitly declared, defaulted, deleted and trivial; the type traits the fragment can state, as judgements of the program; requires-expressions of calls and types; and concept-ids, normalized into the associated constraints.
  • Since phase 15: class templates with bases and members, a specialization's members by substitution when it is looked into, and member templates of class templates.

Out of scope at the start:

  • Name lookup and argument-dependent lookup. The candidate set is an input.
  • The general theory of implicit conversion sequences. One concrete ranking, for priority tags and reference binding, is supplied to assess user-written dispatch. Phase 11 brings the user-defined conversion sequence in.
  • The expression language. Expression validity is an oracle. Phase 12 takes the type traits and requires-expressions the fragment can state out of the oracle, as judgements over the types, the special member functions and the calls the model already decides; the oracle keeps the residue.
  • Multiple translation units and points of instantiation.

What stays open after phase 15, and the order to take it in, is listed under Open areas.

Standing assumption: one translation unit, with every instance declared before any use that would instantiate its lookup. This axiom hides the real coherence hazards of C++, which are ill-formed with no diagnostic required. It is stated explicitly so that a later phase can remove it (Overload.SingleTranslationUnit, tagged assumed "single-tu").

Modelling approach

The model is a deep embedding of a small template language, with each mechanism given twice: as a relation that transcribes the standard, and as an executable function proved to agree with it.

  • Syntax as data. Types, template heads, patterns, constraints and declarations are inductive types. A program is an ordered list of declarations, so declared-before-use is a checkable predicate.
  • Two outcome types. Substitution and resolution each return more than success or failure, and the theorems are about the difference.
  • Expressions are an oracle. An atomic constraint needs only to know whether its substituted expression is valid and whether it evaluates to true. The environment supplies that, so the expression language stays out of the model.
  • Conversion ranking is a parameter. Phase 5 takes a structure giving which conversions exist and a preorder on them. The separability theorem quantifies over that structure.
  • Constant template arguments are structural values. They are trees with decidable equality, and that equality is the model's template-argument equivalence.
  • Every definition cites the draft. Each carries its stable name and paragraph as a checked attribute, such as [temp.deduct.general]/5, so the citation index can be generated and re-checked when the draft moves.
  • Executable means testable. The executable side runs under #eval and drives a generator that emits C++ for the differential tests.

The two outcome types, as they stand in Overload/Outcome.lean:

inductive Subst (α : Type) where
| ok : α → Subst α -- substitution succeeded
| soft : Reason → Subst α -- deduction failure, immediate context
| hard : Reason → Subst α -- ill-formed, diagnostic required
inductive Resolution (α : Type) where
| selected : α → Resolution α
| noMatch : Resolution α
| ambiguous : List α → Resolution α
| illFormed : Reason → Resolution α

Subst gains a fourth case for ill-formed with no diagnostic required when the single translation unit axiom is relaxed.

Traceability to the Standard

Every rule in the model names the sentence of the Standard it transcribes, by stable name, and every statement is filed as a rule, a theorem, or an assumption of ours.

Stable names such as temp.deduct.general survive renumbering between drafts, and clause numbers do not. One paragraph often holds several rules: paragraph 5 of temp.deduct.general holds the whole step order. So a citation is a stable name, a paragraph and a sentence, per citation-granularity.

The citation is an attribute, not a comment, so tools can check it:

@[std rule "temp.deduct.general#5.sentence-6"]
def checkConstraints ...
@[std theorem "temp.func.order#2.sentence-4"]
theorem constraints_only_break_ties ...
@[assumed "single-tu"]
def declaredBeforeUse ...

On a constructor the attribute is written as a command after the inductive, attribute [std rule "..."] Subst.ok, since Lean does not accept attributes in a constructor's declaration (findings.md). A declaration that transcribes several sentences cites them in one attribute, @[std rule "a" "b"]: a parametric attribute keeps one parameter per declaration, so a second std attribute is refused with an error (findings.md).

Three checks follow from it:

  • A lint fails the build when a constructor of a specification relation, or any axiom, carries neither a citation nor an assumption tag (#check_citations in Overload.lean).
  • The citation index is generated from the environment (make citations, citations.md). It lists what rests on each sentence, and which in-scope sentences have no counterpart in the model.
  • When the draft moves, each changed sentence maps to the definitions to re-examine (make drift-check-current).
Class Meaning Form in Lean
Rule A normative sentence taken as given. A constructor of a specification relation, or a clause of a definition.
Theorem A statement in the Standard that the model proves from the rules. A theorem tagged with the sentence it restates.
Assumption Something the model needs that the Standard does not say. A tagged hypothesis or structure field, linked to its decision-log entry.

Normative sentences start as rules. One is reclassified as a theorem when it is proved from the others and then deleted from the rule set, which confirms nothing else needed it. Notes and examples are not normative, so they start as theorems: an example is a test with a stated outcome, and a note that asserts a consequence is a proof target.

Rules are inductive relations and never Lean axioms. An inconsistent set of axioms proves everything, so every theorem would pass silently. An inductive relation cannot be inconsistent, so a conflict in the Standard surfaces as a named theorem that fails. Each headline theorem is audited with #audit (the #print axioms check) and may show only Lean's standard axioms and tagged assumptions.

The four kinds of finding about the Standard are tabulated in findings.md.

Separability suspects

Conversion ranking is expected to factor out of instance selection. The exposure is elsewhere: the order of deduction steps, and whether a failed lookup is soft or hard. Each suspect below becomes one lemma under the separability theorem.

Instantiations triggered by substitution are outside the immediate context ([temp.deduct.general]/8). A lookup in a defaulted constant parameter runs for every candidate deduction reaches, including ones that would lose. A requires-clause on the same template cannot guard it. Instance inheritance

The hypothesis is that inheritance between instance types is selection-inert exactly when every use site takes the instance at its deduced exact type. This is the question tracked as instance-inheritance, decided 17 October 2026: inheritance is allowed, and what it costs is harvested as obligations.

The typeclass technique itself needs no subtype relation between instance types. Use is duck typed, and the weaker instance can be derived from the stronger one: a Monad instance's as_functor returns derive_functor<M>, a fresh type that supplies the Functor operations from the Monad ones. The relation varies by kind and may vary within a kind. Nothing forbids an implementer from using inheritance instead, so the guidance has to say whether that is safe.

Once a signature names an instance type concretely, inheritance becomes a second ordering beside concept refinement, and the two can disagree. Four leaks are known:

  1. Ranking beats subsumption. Derived-to-base is a ranked conversion, and conversion comparison is consulted before constraints. An overload that should win by refinement can lose on rank. Confirmed 17 October 2026 (rank_beats_refinement, leak_rank_*.cpp): an overload naming an Applicative instance type wins at that type and loses to a generic template at a Monad instance type derived from it.
  2. Deduction from a derived class. A function parameter of the form functor_impl<F> deduces from a class derived from it, and fails if more than one base matches ([temp.deduct.call]/4). A derived Applicative silently matches Functor-shaped signatures. Confirmed 17 October 2026 (derived_class_deduction, leak_derived_deduction_*.cpp): a Monad instance type derived from derive_functor<I> matches a parameter const derive_functor<I>&, and stops matching once the derivation is replaced by composition.
  3. Two paths to the superclass. Slicing an Applicative to its base gives one Functor and lookup gives another. They agree only if the base is the canonical instance, and the explicit-instance routes do not force that. Recorded 17 October 2026: in the model the two are different template arguments whatever their behaviour (superclass_identity).
  4. Constant-parameter conversion. Whether a derived instance is accepted for a base-typed constant template parameter is unchecked, and is a candidate for compiler disagreement. Settled 15 October 2026: accepted and sliced under C++26 (probes.md), so the leak is live. A theorem since 21 October 2026 (slicing_identifies), with the reference parameters the library uses as what closes it (reference_keeps_identity).
  5. Conversion between instance types. A converting constructor or a conversion function from a Monad instance type to an Applicative instance type is the other way to write refinement in the type system. Theorems since 23 October 2026, phase 11: deduction never applies it (conversion_invisible_to_deduction), ranking puts it below every standard sequence (conversion_loses_rank, converting_sites_ambiguous), and its result is a temporary, which the pinning routes refuse and the value route identifies with every other value that converts (converted_instance_temporary, value_route_identifies_converted). The encoding avoids this leak by design rather than suffering it: refinement by shape is the obligation (obligations.md).

Two theorems settle it. Inheritance erasure is the positive result: inside the exact-type fragment, inheritance is only an implementation convenience. Superclass coherence is a law on instance authors in every case, because derive_functor<M> is a different type from the canonical Functor instance, so the two can only agree in behaviour, never in identity. Leak 3 is therefore live today: a data type with a canonical Functor instance and a Monad instance has two Functors, and nothing in the language makes them agree.

Outside the fragment the model should produce a concrete counterexample for each of leaks 1 to 3. The expected guidance is a checkable rule: inherit if you like, but never name an instance type in a signature.

Proof obligations

The obligations are harvested, not enumerated: every hypothesis a theorem needs that the language does not guarantee is an obligation on someone. The list is then complete relative to the theorems, and each entry has a proof showing why it is needed.

The algebraic laws of each typeclass were excluded at the start; phase 13 names them as semantic requirements, cited where the Standard states the kind, with the theorems that owe each listed by #owes, and still proves none. These are the obligations of the mechanism.

Each obligation is classified by how it is discharged:

  • By construction. The library's design makes violation impossible.
  • Compiler-checked. Violation is a required diagnostic.
  • Library-checkable. A concept or static_assert can catch it.
  • Undiagnosable. Violation is ill-formed with no diagnostic required, so only convention or tooling stands behind it.

Algorithm-author obligations

Planned 18 October 2026. The obligations above belong to typeclass authors, instance authors and users of explicit instances. A fourth party writes an algorithm that needs an Applicative or a Monoid and takes one, auto&& app or a policy parameter. Some obligations carry over to that author unchanged, since the algorithm is one more operation object over an instance. Others come from where the algorithm sits, between a caller and an instance it did not choose. Each question below is sized by the algorithm probes (probes.md) at beman.transpose 30a707d.

The weighing is for accident, not malice. A gap matters by what an ordinary mistake does. Worst is a program that compiles and gives a wrong answer. Next is a check that says yes and a call that then fails; then a hard error where a clean no was owed. A gap whose cost is only a worse diagnostic is weighed against what closing it costs and what it forbids. A case it forbids only matters if the case would otherwise have worked.

algorithm-constraint-accuracy

Does the algorithm's constraint have to imply its body? It is the accurate-members obligation again, owed by the algorithm. With a deduced return type, a weaker constraint makes every check of the call a hard error. Width: as wide as the members it calls. The library's own traverse and transpose objects answer every probe correctly. A violation is safe, since nothing compiles that should not. It matters only when someone checks the call, and that is what an algorithm meant to be built on gets. Cost: a trailing return type or restated constraints. Restating is close to free when the members are accurate, because the constraint is the conjunction of the member calls. Recommendation: owe it for algorithms offered for others to constrain on, not for leaf code. The Lean side is algorithm_transfer, below.

callable-copying

May a member copy the callable it is given? The probes say the concepts' witness is a good proxy except on this one axis. The three failures in 88 cells are all the callable being copied: zip_list copies into a local, and the sender copies into its deferred work, which it must do. The silent one is zip_list running a copy of a stateful lvalue callable, so the caller's object never changes. The Standard's answer for its own algorithms is the note in [algorithms.requirements]/9: they may copy function objects freely, and reference_wrapper is the way to keep identity. std::ref works through every instance probed. Forbidding copies would forbid deferred contexts, which cannot hold a reference to the caller's callable. Recommendation: adopt the Standard's rule. An instance may copy. An instance that copies says so in its constraint (constructible from the argument), which turns the sender's yes-then-fails into a clean no. An algorithm that needs identity passes std::ref. Nothing that works today is lost.

result-context-formable

Must a member's constraint check that its result context exists? invoke with a void-returning callable names std::optional<void>, a hard error. Width: every member whose context cannot hold the result. Safe, and a plausible accident, since a lambda written for its side effect returns void. Cost: one concept per context. It forbids nothing that compiles today. Recommendation: fold it into the instance's accurate members rather than make it a separate obligation.

instance-coherence

May an algorithm given an instance also reach the canonical one for the same context? A slip through an operation object, or through bind, under the accumulating object keeps the first error and drops the rest. It compiles silently. Width: today the only same-carrier pair is std::expected's two applicatives, and they differ in evidence, never in whether the result fails. The library keeps a value-changing alternative, the zip applicative, apart by giving it its own carrier, zip_list. Nothing in the language can check the obligation. Cost of a mechanism: high, and it would forbid the ordinary use of operation objects inside algorithms. Recommendation: an algorithm-author obligation by convention, "take every operation on a context from the object you were given", plus a typeclass-author obligation, "an alternative instance that changes values gets its own carrier; one that changes only evidence may share it as an explicit object". The model has no second instance for one key, so a theorem would need a modelling decision first. Not planned.

capability-tests

Can an algorithm ask what an object can do? monad_object of the accumulating object is a hard error, because its bind is a static_assert in a deduced body. The accumulating object is the one a caller passes to traverse. So an algorithm generic over applicative and monad objects, dispatching with if constexpr (monad_object<P, C>), fails to compile on the object it was meant for. Safe, but it blocks the obvious dispatch. Cost: replace the static_assert with a deleted function, = delete("…") keeping the message, which is a clean no on a check. Nothing is forbidden. Recommendation: an obligation on typeclass and instance authors that a refused operation is refused as a constraint, and an upstream issue for the accumulating bind. traverse's own capability test, collect, answers correctly.

typeclass-refinement

Can a stronger object be used where a weaker one is asked for? No registered monad object is an applicative object, so traverse refuses monad<optional> as a policy, cleanly. No registered object satisfies both concepts either, so overloads on the two are never ambiguous today. monad_object is not written in terms of applicative_object, so a user object that satisfies both makes such overloads ambiguous. Width: narrow, since applicative<C> is registered wherever monad<C> is. Cost: deriving the Applicative members in derive_monad is moderate. Recommendation: when Monad comes to refine Applicative, write monad_object as applicative_object && …. This is the plan's visible-refinement obligation, which nothing has needed yet. No change now.

instance-state

May an algorithm make a fresh instance of the type it is given? lifted_monoid and kleisli_monoid do, with APPLICATIVE_OBJECT{}. A stateful object, such as one carrying an allocator, scheduler or log, is silently not consulted. Every registered typeclass object is empty, so requiring emptiness costs the library nothing today. It would forbid stateful policies, which traverse already supports by taking the object. lifted_monoid itself is not empty, so the rule cannot extend to monoid objects, whose state monoid.hpp allows. Recommendation: an algorithm either uses the object it was passed or requires std::is_empty_v of the type it constructs. For lifted_monoid and kleisli_monoid, holding the object as a [[no_unique_address]] member does both at no cost. Upstream issue.

instance-exact-type

Must an algorithm take its instance at its exact type? Yes, as for operation objects, since members are found by static type. Width: nil in practice. Spelling a base requires an exposition-only name, and the one probe through a base reference gives the instance's answer. Recommendation: fold it into the existing exact-type row; no probe or theorem beyond the one there.

Phase 9: declarations and where to find them

Planned 20 October 2026. The candidate set of a call is an input to the model, and decisions.md#lookup-scope said name lookup was out of scope. Several of the model's load-bearing claims are nevertheless claims about lookup, made in prose with no rule behind them:

Phase 10: template arguments and their conversion

Planned 21 October 2026. A constant template argument in the model is a structural value, Ty.value, and the only check an explicit argument gets is kindMatches: a value for a constant parameter, a type for a type parameter, with the parameter's declared type ignored. A default argument is formed and bound as it is. The declared types are formed by parameterListStep and discarded. So template <signed char> f accepts f<1000>, a template <bool> accepts f<2>, and a base-typed class parameter accepts a derived value unchanged, which makes X<derived> and X<base> different specializations where the Standard says they are the same. The draft's own example, [temp.deduct.general]/12, is the first of these, and citations.md listed it and [temp.arg.nontype]/1 and /3 as in scope with no counterpart.

The conversion is what [temp.arg.nontype] specifies after P2308R1, Template parameter initialization (adopted November 2023, draft commit 97ca5cf3): for a non-class type the argument is a converted constant expression of that type, which admits integral promotions and non-narrowing integral conversions ([expr.const.const]/8, [dcl.init.list]/7); for a class type a temporary constexpr T v = A; is introduced and the parameter's value is v's, so a derived value is sliced ([temp.arg.nontype]/3 to /5). That rule is behind the constant-argument probe of probes.md, where Clang accepts and slices and GCC applies the pre-P2308 text, and behind leak 4 of decisions.md#instance-inheritance. Phase 10 makes both theorems with cited rules, and gives the argument-conversion suspect above its "second, unranked conversion relation".

Design

The conversion runs in the two steps where template arguments enter the bindings, so that deduceTemplate's chain and every theorem about it are unchanged apart from one new env argument: explicitStep env head explicit converts each explicit argument against the parameter's declared type substituted with the earlier explicit bindings ([temp.names]/13 bullets 3 and 4), and defaultsStep converts the formed default (a default template argument is an initializer-clause for the same invented declaration, [temp.arg.nontype]/1). A failed conversion is soft, like a wrong kind today. convertArg is total and never hard; its cases, in order, are the constructors of ConvertsTo: a type for a type parameter; a placeholder anywhere in the declared type, identity; a dependent declared type, identity until parameterListStep forms it; an integer type, convertedConstant; a class value of the parameter's class, identity; a class value of a derived class, the base subobject through Env.subobject; an lvalue reference and a .ref, identity. Env gains that one oracle, subobject, computed by Program.subobject with the fuel pattern of derives, so erasure's induction carries over. Structural types stay out of the deduction path: an Env.structural oracle would need a second congruence hypothesis, and erasing a protected base turns a non-structural class structural, so inheritance_erasure could not discharge it. Program.structural is a program-level predicate.

Phase 11: user-defined conversions

Planned 23 October 2026. The lower model forms two implicit conversion sequences, the identity and derived-to-base, and binds a reference directly or not at all (Overload/Ranking.lean). That is what the typeclass encoding needs, and the general theory was put out of scope at the start. The question the model cannot answer as it stands is why the encoding has no converting constructors between instance types, and whether it should. A Monad instance that converts implicitly to an Applicative instance looks like a way to write refinement in the type system. The encoding writes refinement as a concept on the instance's shape and a retrieval function, derive_functor<M>, and takes instances at their deduced type. Phase 11 adds user-defined conversion sequences to the Standard side, so that the reasons are theorems and the lower model answers questions about calls wider than the encoding's.

Four rules do the work. A user-defined conversion is not among the three differences deduction tolerates between the deduced and the actual argument type ([temp.deduct.call]/4), so a conversion between instance types fires at no deduced parameter, which is every generic algorithm. A user-defined conversion sequence is worse than every standard conversion sequence ([over.ics.rank]/2), so a generic template beats an overload naming the converted-to type, and two such overloads reachable by different conversions are indistinguishable ([over.ics.rank]/3, the user-defined bullet). The result of a conversion is a prvalue: a reference binds a temporary ([dcl.init.ref]/5), a reference constant parameter refuses it ([temp.arg.nontype]/6), and a class-typed value parameter copy-initializes from it ([temp.arg.nontype]/3), so every source that converts to one value names one specialization ([temp.type]/1). An explicit constructor or conversion function is no candidate for copy-initialization ([over.match.copy]/1, [over.match.ctor]/1, [class.conv.fct]/4), and argument passing is copy-initialization ([dcl.init.general]/13), so an explicit conversion fires nowhere an instance is passed. This is the mirror of inheritance leak 2: derivation is visible to deduction and diverges from refinement one way, conversion is invisible to deduction and diverges the other.

Casts stay out. An explicit conversion is an expression, and the fragment has none (decisions.md#expression-depth). What explicit does is modelled: the initialization context, copy or direct, is a flag on the initialization rather than a syntax.

Phase 12: the type system, special member functions and traits

Planned 24 October 2026. The model's types are what deduction needs: a name, a parameter, const, a pointer, the two references, a specialization and a constant argument (Ty). A class is a name with bases, and since phase 11 its conversions. Every type trait and every concept the encoding's constraints use is an atomic constraint with a string for its expression, answered by the environment's oracle (Constraint.Oracle, decisions.md#expression-depth). So the model can say which candidate a constraint selects, and not why the constraint holds, and nothing it proves about the encoding's concepts rests on what the concepts say. Phase 12 widens the lower model in three directions that depend on one another: the type categories of [basic.types] and the data members of a class; the special member functions, implicitly declared, defaulted and deleted; and the type traits and requires-expressions as judgements computed from those, with the oracle kept for the residue.

The order is forced by dependency. The traits that look like compiler magic are nearly all questions about special member functions or class layout. is_copy_constructible is overload resolution over the constructors with the usable-candidate check. is_trivially_copyable is eligibility and triviality of the copy and move members. is_standard_layout is a predicate on members and bases. Modelled before the special member functions they would be more oracle strings. The special member functions in turn need data members, since every deletion rule is a rule about a member or a base subobject. And the structural traits, is_same, is_reference, is_class, cost nothing once the type categories are named, and retire half of the oracle at once.

Two consumers wait on the typeclass side. The callable-copying obligation says an instance that copies its callable should say so in its constraint, so the sender's yes-then-fails becomes a clean no. That is a theorem once is_copy_constructible of a class with a deleted copy constructor is a judgement and not an oracle answer. The typeclass-refinement obligation writes refinement as a concept on the instance's shape. With concept-ids normalized, the superclass's atoms appear in the refined concept's normal form with the identity mapping, and the subsumption is computed where today a test states it as an atomic identity.

The Standard has no words for value and reference semantics as properties of a type. The nearest are object type and reference type ([basic.types.general]/1, /6). The phase gives the model two definitions under the author's names, data and codata: an int is data, an int& is codata, and a reference member gives the enclosing class a codata nature. That has an exact rendering in the rules, as a theorem and not a rule. A reference member without a default member initializer deletes the defaulted default constructor ([class.default.ctor]/2), and a reference member deletes the defaulted copy and move assignment ([class.copy.assign]/7); a const non-class member deletes assignment too; and a member or base whose corresponding special member is deleted deletes the enclosing one ([class.default.ctor]/2, [class.copy.ctor]/10, [class.copy.assign]/7, [class.dtor]/7). So for a class that declares no special member of its own, every defaulted special member is non-deleted exactly when no member, through class-typed members likewise, is of reference type or const non-class type. Pointers mark the limit of the idea. A pointer's codata aspect is aliasing of what it points to, which is a question about the object model, and the fragment has no object model. The type system says a pointer is data: a scalar, trivially copyable, and it deletes nothing. The scope statement is decisions.md#value-nature, so the model does not promise more.

Design

  • Types. Ty gains one constructor, fn (params : Ty) (ret : Ty), the function type ([basic.compound]/1), with params a nil/cons chain so every proof stays an ordinary induction. Deduction treats it as it treats spec, structurally; the forms T() and T(T) of [temp.deduct.type]/8 are already in scope. The predicates of [basic.types.general] are functions on Ty: isObject, isReference, isFunction, isScalar, isClass, isIntegral, isCompound, isConst, with removeConst, removeReference, removeCvref and addLvalueReference beside stripConst. Decl.function and FunctionTemplate have a return type already (ret, defaulting to void); the compound requirement and is_invocable_r read it. Adding a constructor to Ty touches every deduction induction; the cost is paid in stage 2, while it is one constructor and nothing depends on it.
  • Members. A data member is its own declaration after its class, Decl.member cls m, as a conversion is, with Member a name, a type and whether it has a default member initializer; Program.membersOf lists a class's in order. The plan had them as a field of Decl.class; a separate declaration keeps the flat program and every match on Decl.class, the reason phase 11 gave for Decl.converting. Members are public and non-static; a member's type may be a reference, a const type, a pointer, a scalar or another class. Program.subobjectsOf is the potentially constructed subobjects ([special]/7). Erasure (Overload/Erasure.lean) carries members untouched, as it carries bases.
  • Special members. SmfKind is the six kinds. A class declares special members as SmfDecl := { kind, body : SmfBody, constParam : Bool } with SmfBody one of .userProvided, .defaulted, .deleted; Decl.class gains special : List SmfDecl. Program.specialMembers c is the set of [special]/1: the declared ones, and for each kind not user-declared the implicit one by [class.default.ctor]/1, [class.copy.ctor]/6 and /8, [class.copy.assign]/2 and /4, [class.dtor]/2, with its parameter form by [class.copy.ctor]/7 and [class.copy.assign]/2. Program.deleted c k is "defined as deleted" for a defaulted member, the bullets of [class.default.ctor]/2, [class.copy.ctor]/10, [class.copy.assign]/7 and [class.dtor]/7, recursive through the subobjects' classes via resolve over their constructors or assignments and the usable-candidate check ([over.match.general]/4), fuel-bounded by declaration order as derivesWithin is. Program.trivial c k likewise. Program.eligible is non-deletion ([special]/6). The relation is SpecialMember, the function specialMembers, the agreement specialMembers_iff; deleted_iff and trivial_iff the same for the two judgements. Program.constructors c and Program.assignments c are the candidate lists: the special members by signature and the Decl.converting constructors, less a deleted defaulted move member. Program.userConversions draws its constructors from constructors from here on, so a deleted copy constructor is a candidate that resolution may select and the usable check then refuses, as [dcl.fct.def.delete]/2 says.
  • Value nature. Program.valueNature c: every special member of c is defaulted and non-deleted. Program.referenceMember c: some subobject of c, or of a class-typed subobject's class likewise, is of reference type or const type. value_nature_iff: for a class whose special members are the rules' own, through its class-typed subobjects to any depth (implicitClass), valueNature holds iff referenceMember fails. pointer_member_keeps_value_nature: a pointer member deletes nothing. deletion_propagates: a member or base of class M with a deleted corresponding special member deletes the enclosing defaulted one, through any depth. These are definitions and theorems; no cited sentence states them, and the data and codata names stay in the docs.
  • Traits. Trait is an inductive of the queries the fragment can state, with the arity each takes; Program.trait q args : Subst Bool answers them by the rules above. Constraint gains .trait (q : Trait) (mapping : List Ty) beside .atomic, with identity by structural equality ([temp.constr.atomic]/2) and satisfaction by Program.trait on the substituted mapping, an invalid substitution in the immediate context giving false ([temp.constr.atomic]/3). Constraint.atomic and the oracle remain for the residue, so every existing case stands. trait_is_resolution: is_constructible, is_assignable and is_convertible are resolve plus usable over the class's candidates with the argument, so the trait's answer is the call's; is_convertible_eq_ics names the phase 11 sequence.
  • Requires-expressions and concept-ids. Constraint gains .requires (params : List Ty) (reqs : List Requirement) and .conceptId (name : String) (args : List Ty); Decl.concept's body becomes a Constraint, with the string body kept as .atomic for the existing cases. Requirement is .simple call, .type t, .compound call constraint, .nested c, where a call is a callee and argument types over the requirement's parameters, decided by callAt. Program.normalize expands concept-ids ([temp.constr.normal]/1), fuel-bounded by declaration order, since a concept names only concepts declared before it. Satisfaction of .requires is in lexical order, a soft failure of any requirement is false, a hard one is hard ([expr.prim.req.general]/5): requires_soft_is_false, requires_order, compound_eq_simple_nested. Subsumption (Overload/Constraint.lean) runs on the normal form, so a refined concept subsumes its superclass's concept-id structurally.
  • The call and the emitter. Program.call gains the usable check on the selected constructor of a copy-initialized class parameter, beside access and the ambiguous sequence. Overload/Emit.lean renders members, special member declarations with = default and = delete, and a trait or requires-expression as a static_assert on the std:: trait or the concept, so every trait judgement is differentially tested against the compilers' own answers.
  • The encoding. Overload/Typeclass/ValueNature.lean: instance_shape_regular, an instance type with no data members and no declared special member has every special member defaulted, non-deleted and trivial, so it is trivially copyable and empty; copy_constraint_shields, a member constrained by is_copy_constructible of its callable fails softly at a callable with a deleted copy constructor, where the body's copy would be a hard error, the callable-copying rule as a theorem; reference_member_instance, an instance type that holds a reference is structural for the value route ([temp.param]/12) and not assignable, so the two notions do not coincide; nested_reference_instance, the reference nature reaches an instance through two class-typed members, by value_nature_iff; refinement_normalizes, the refined concept's normal form contains the superclass's atoms with the identity mapping, so the refinement subsumes with no hand-written identity, the typeclass-refinement obligation's mechanism; member_probe_accurate, a requires-expression over a member call holds exactly where the call is viable and well-formed, which is the accurate-members obligation stated as the Standard states it.

Phase 13: semantic requirements, what satisfies and what models

Planned 24 October 2026. Phase 12 made every constraint the fragment can state a judgement: a trait is computed, a requires-expression is decided, a concept-id is expanded. What none of that reaches is the half of a concept's specification that is not a constraint. [res.on.requirements]/1 says a sequence of template arguments models a concept when it satisfies it, which is [temp.constr.decl], and meets all semantic requirements given in the concept's specification; /2 says a program whose validity depends on modelling, where the arguments satisfy but do not model, is ill-formed, no diagnostic required. The library's concepts each carry such requirements: copy_constructible that the copy is equal to the original and leaves it unmodified ([concept.copyconstructible]/1), equality_comparable that == says true exactly for equal values ([concept.equalitycomparable]/2), regular_invocable that the call is equality-preserving ([concept.regularinvocable]/1), which is the whole of its difference from invocable (/3). The typeclass laws are requirements of the same kind: an instance whose fmap has the right shape satisfies the Functor concept, and one whose fmap preserves identity and composition models it. The plan so far excluded the algebraic laws from the obligations table. Phase 13 brings them in, not as things proved but as things named: a semantic requirement is a cited, slugged statement that nothing decides, modelling is satisfaction plus hypotheses, a theorem that needs a law says so in its statement, and an audit lists the laws each headline theorem rests on. The verdict of [res.on.requirements]/2 joins the ill-formed-no-diagnostic verdicts of Units: it is the precise sentence for "the compiler cannot catch this".

Two things the phase does not do. It does not check a law, since the fragment has no expressions to evaluate and a law is a statement about values; and it does not encode a law as a decidable property, since that would be a second, unverified transcription of the same prose. Its value is that every law has one name, one citation, and a list of the theorems that assume it.

Design

  • A semantic requirement. Semantic is a slug and a statement, the slug kebab-case and named for the question, the statement the requirement in words, with the citation on the Lean constant that defines it. Nothing decides one: Laws := Semantic → List Ty → Prop is the oracle, a hypothesis a theorem states. The Standard's are in Overload/Concepts.lean; the encoding's laws, which the Standard does not state, are in Overload/Typeclass/Laws.lean with their source in the statement. Decl.semantic concept law attaches a requirement to a concept's specification, its own declaration after the conceptDef, as a member or a conversion is after its class.
  • Modelling. Program.laws c is the requirements of c's specification and, through the concept-ids in its body, of the concepts it is defined in terms of: modelling regular is modelling semiregular and equality_comparable. Program.models env laws c args is satisfaction of the normal form of c<args> and every law held; models_satisfies is the one direction the text gives.

Program.conceptUses takes the selected candidate of a call and lists the concept-ids its template's constraint-expression names, with the deduced arguments substituted, which are the uses the call's validity depends on ([res.on.requirements]/3).   • The library's concepts. Trait.isNothrowDestructible is added, equal to isDestructible by [class.dtor]/6. Phase 14: virtual functions, exception specifications and aggregates

Planned 24 October 2026. Three parts of the type system that the traits of phase 12 reach for and the fragment does not have. A virtual function makes a class polymorphic, takes every special member's triviality with it, and makes an abstract class one no object can have. An exception specification is a predicate on every function, explicit or implicit, and the whole is_nothrow_ family is one rule over it. An aggregate is what a class with no user-declared constructor is, and aggregate initialization is what T{} and, since C++20, T(args) mean for it, which is also what the model's class values have been all along: a value is its elements. Each is a stage, each closes with its own docs and citations, and each extends the same machinery, the special member judgements of phase 12 and the resolution they rest on, with one new fact about declarations.

Two corrections come with the third stage. The model's class value, Val.obj, lists base subobjects and nothing else, and phase 11 rested "one value per class" on it; with data members since phase 12 that is wrong for a class with a scalar member, and the aggregate's elements, bases then members ([dcl.init.aggr]/2), are what the value should list. And phase 13 took T{} and T t; to be one condition in default_initializable; for an aggregate with a const member they differ, and the stage separates them.

Phase 15: class templates and their members

Planned 25 October 2026. The fragment's class templates are template <head> struct name {}; with nothing inside. Decl.classTemplate has a name, a head and a scope, no bases and no members, and nothing in the model looks inside a specialization: Program.directBases gives X<int> no bases, Program.memberScope? finds no scope for it, and so is_invocable<X<int>, A> has no call operators to find, the trait inherits that, and the decision log carries it as residue (decisions.md#trait-residue). The residue wording was a symptom. What is missing is members of class templates in general: declarations stated in the head's parameters, the substitution of a specialization's arguments into them when the specialization is looked into, and the instantiation and point-of-instantiation rules that say when that happens and what it produces.

That is also the shape the encoding has and the model has stood in for. beman.transpose's derivation base is template <class Impl> struct derive_functor : protected Impl, with member templates fmap and replace constrained by requires-expressions over Impl (src/smd/overload/encoding.hpp), and an instance is a specialization of it. The model declares derive_functor as a plain class where it needs the name (Overload/Typeclass/Lookup.lean, Overload/Typeclass/Inheritance.lean), names an instance's value by the type instance_of<a, i>, and answers the operation object's constraint, TC.fmap(declval<F>(), declval<T>()), by an oracle that says true exactly when the lookup selects an instance (memberAtomics, Overload/Typeclass/Encoding.lean). Every theorem about the instance's members takes that answer as a hypothesis (Overload/Typeclass/Members.lean), and the accurate-members obligation rests on an audit, not a computation. With class template members the member call is resolved on the instance's type, the hypothesis becomes a theorem about the computed environment, and the derivation base's accuracy is a theorem about the reduced encoding.

The phase is the Standard side first. A class template gets bases and members, a specialization gets the template's member declarations with its arguments substituted, member lookup and the call on an object are keyed by type rather than class name, and the traits and special members follow because they are already keyed by type. The typeclass side then declares the real derivation base and resolves the member call. Explicit and partial specializations of class templates stay out: the encoding's instances are partial specializations of a variable template, which the model has had since phase 1, and the members of an explicit or partial specialization are unrelated to the primary's ([temp.expl.spec]/6, [temp.spec.partial.member]/1), so admitting them would be a second member mechanism for no consumer.

Design

  • Members of a class template. A member, a special member and a conversion of a class template are Decl.member, Decl.special and Decl.converting for the current instantiation, ‘currentInstantiation n h = .spec’ n [.param 0, …], exactly the spelling the Standard uses for an out-of-line member,A<T1,T2>::f1. A member function or member function template is aDecl.functionorDecl.functionTemplate whose scope ends in.class n, as a class's does, with the class's parameters as.param i.Decl.classTemplategainsbasesand protectedBases, which may be dependent:derive_functor : protected ImplisprotectedBases := [.param 0]. The flat program stands, and Decl.isMember` is unchanged.
  • Member templates. A member template's own head follows the class's in the numbering: with a class head of length n, the member's jth own parameter is .param (n + j) in its declaration. Program.specializationBindings? (.spec n as) runs explicitStep and defaultsStep over the class head, as validType does, and Decl.instantiate substitutes with the argument list ‘as’ ++ [.param 0, …, .param (own - 1)]throughConstraint.substArgsandTy.subst`, which are single-pass, so the class's arguments go in and the member's own parameters come out renumbered from zero in one substitution. The emitter names a parameter by its index, so the class's are T0, … and the member's own continue the count, which is what C++ needs for the two heads. A ground class has σ = [] and Decl.instantiate is the identity on it (instantiate_ground), so the ground and template cases are one code path.
  • Instantiation on lookup. Program.classKey? : Ty → Option (Ty × Bindings): a class name is itself with no bindings; a specialization of a declared class template with a valid argument list is the current instantiation with the bindings; anything else is none. membersOf, specialDecls, conversionsOf, directBases and declarationSet look the key up and instantiate what they find. The lookup set over bases, lookupSetWithin, recurses through directBases, which are substituted first, so the merge of [class.member.lookup]/4 sees no dependent base. Subobject becomes List Ty. Every function of Overload/Members.lean that took a class name takes a type: memberSearch, callOperators, surrogates, objectCandidates, impliedObject, objectCallAt, memberCallAt, and classCallee in Overload/Requires.lean returns the type. Program.trait and Program.special are already keyed by type and need no change beyond the primitives beneath them.
  • The member call's object. memberCallAt leads with impliedObject cls, the const lvalue the object call uses, and the found members carry their implicit object parameter through Decl.withImplicitObject. The fragment's member functions are all const, so the object binds by the identity and no earlier resolution changes; member_call_object_inert says so for the concrete programs that exist, and the general inertness theorem the surrogate stage owes is stated for both calls at once.
  • Point of instantiation. Program.pointOfInstantiation c is the position of the first declaration that mentions c, where [temp.point]/4 puts the point for a specialization referenced from a non-template context. Program.templatesWellFormed: every member of a class template follows its declaration and precedes that point, for every specialization the program mentions. Under it, the member search of a specialization is the same from every position at or after the point (specialization_members_fixed), which is what "at most one point of instantiation" means for a model without definitions. The dependent-call machinery of phase 9 is untouched: a member call on a specialization is not a dependent call, since its callee is not an unqualified-id.
  • The typeclass side. Decl.instance gains value : Option Ty, the type of the instance's value, mentioning the pattern's parameters; Env.ofProgram's instantiate returns it with the pattern's deduced bindings substituted, and instance_of<a, i> stays the name when none is given, so every existing theorem about lookup is unchanged. derive_functor is declared as the class template it is, with fmap and replace as member templates constrained by the requires-expressions of the header, over the member-call requirement on const Impl&. Env.fullWithin answers fmap_call one level down, as it answers a requires-expression and a class-callee trait: the member call TC.fmap(declval<F>(), declval<T>()) on the value type with the lookup's object as implied object argument (Program.memberInvoke). memberAtomics is retired, and ofProgram_member is restated: the computed environment is the accurate member exactly when the value type's fmap is accurate, and derivation_base_accurate shows the reduced header's is. The hidden-member program of Overload/Typeclass/Lookup.lean is restated on the real shape.
  • Emitter. A class template renders with its bases, data members, special members, conversions and member functions, the last with their own heads, as a class does; the head renderer takes an offset for a member template's own parameters. An instance with a value type renders inline constexpr value tc<pattern>{}; the emitted encoding cases that test which instance was selected through selected<k> are restated to test the value type.

Open areas, to be picked up next

Written 26 October 2026, after phase 15 closed, as the list to open the next planning session with. The target has moved: beman.transpose is now part of beman.typeclass, and the encoding under study there carries Applicative and Monad beside Functor, with sender/receiver of std::execution as an instance type and as a consumer. Each area below is recorded as the plan records a suspect: a slug named for the question, what the fragment lacks, what the Standard says about it, and what the encoding needs it for. The order is by how much of the Standard each holds and how much the encoding leans on it. None is a phase yet; a phase is planned from the draft when one is picked up.

expression-fragment

The model has no expression language. Validity is an oracle, a concept body's comparison or ranges::swap is a residue atom, and a return type is declared, never computed. Every auto function in the encoding returns what its body returns, and the model cannot say what that is, so invoke_result_t, decltype((E)) on anything but a declared call, and the result types of fmap and replace are all outside it. Every other area here bottoms out in this one. The fragment the encoding uses is small: calls, member calls, std::forward and std::declval, and bodies that are one return of a call. A typed fragment of those, with the return type of such a body computed by [dcl.type.auto.deduct]/2 from [expr.call]/4 and [dcl.type.decltype]/1, covers it without taking on constant evaluation or the rest of [expr]. Sender/receiver adds connect, start and the completion signatures, which are the same shape: calls whose result types are what matters.

parameter-packs

Ty has no pack. The finding on invoke_fn already says its trailing pack is outside the fragment. Applicative's invoke(f, args...) and Monad's bind through it, std::execution's completion_signatures and set_value(Vs...), and every variadic class template of the library need pack deduction ([temp.deduct.type]/9, /10, [temp.deduct.call]/1 last sentence), pack expansion in template argument lists and function parameter lists ([temp.variadic]), sizeof..., and fold-expanded constraints ([temp.constr.fold]). This is the structural piece that gates the next typeclasses, and it is mechanical beside the expression fragment: Ty gains a pack parameter and an expansion, and every proof by induction on Ty gains a case.

closure-types

The fragment's callables are named function objects. Callers pass lambdas, whose closure types have their own rules ([expr.prim.lambda.closure]): a templated call operator for a generic lambda, conversion to a function pointer when captureless, copyability and triviality from the captures, const on the call operator unless mutable. The callable-copying theorem and the value-nature theorem are stated without them, and the sender probe's move-only callable is a closure.

type-computation

remove_cvref is a constructor of Ty. There is no alias template, no common_reference, no general metafunction, so a trait the encoding spells through an alias is either hard-wired or out. Alias templates ([temp.alias]) with their non-deducibility, and decltype over the expression fragment, would cover what the encoding writes; completion_signatures manipulation in std::execution is alias computation over packs.

template-definitions

Explicit and partial specializations of class templates ([temp.expl.spec], [temp.spec.partial]) with their own member sets and the partial ordering of partial specializations; and anything that happens inside a template definition: dependent names, the current instantiation as a lookup scope, two-phase lookup ([temp.res], [temp.dep]). Every use in the fragment is outside every class, so none of it runs. A derivation base whose fmap calls Impl::fmap is a dependent call inside a definition, which phase 15 declared and did not look into.

translation-units

The single-translation-unit axiom (decisions.md#single-tu) hides the ill-formed-no-diagnostic coherence hazards that motivated the lookup theorems. Points of instantiation across units ([temp.point]), the one-definition rule ([basic.def.odr]) and modules are where instance coherence lives. Small as syntax, this is the largest open area for the typeclass question, and phase 8 of the table is its placeholder: it would change what the existing coherence and stability theorems mean rather than add new ones.

list-initialization

Braced initialization is residue in the traits, deduction from a braced-init-list is out ([temp.deduct.call]/1), and is_aggregate's use with it. [over.match.list] and [dcl.init.list] are the rules. std::execution's just(vs...) and the tuple-shaped senders are where the encoding meets it.

type-breadth

Enumerations, unions, arrays, pointers to members, floating-point types, volatile, virtual bases, final. Each is small except virtual bases, which touch lookup, dominance and every special member ([class.mi]/4, [class.member.lookup]/6, [class.virtual]/2, [special]/7), and arrays, which touch deduction through decay ([temp.deduct.call]/2).

deduction-guides

Class template argument deduction and deduction guides ([over.match.class.deduct]). Out, and nothing in the encoding needs them; recorded so the omission is a decision.

Where to start

Applicative and Monad need parameter-packs and the expression-fragment with computed return types, in that order: the pack is the syntax and the return type is the meaning. Sender/receiver needs those two and type-computation over the completion signatures. translation-units is the one that changes what is already proved, and should be planned once the typeclass side has the three typeclasses to state coherence over.
